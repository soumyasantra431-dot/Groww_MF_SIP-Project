# Discovery-engine presentation benchmark — 6 November 2026

**Decision served:** make the Groww SIP engine understandable to a new evaluator in two minutes while preserving evidence integrity. These are presentation and workflow references, not evidence about SIP investors. Public project status and “Top Fellow” status were not independently verified for every example. I inspected seven live interfaces and eight other public project repositories; two further live links were login/loading blocked and did not inform the design.

## Live interfaces inspected

1. [Google Photos Discovery Engine (blue)](https://google-photos-discovery-engine-blue.vercel.app/) — names the problem, places corpus units near the top, then lets the viewer select an area and open evidence and contrasting cases. Its many counts require careful denominator wording.
2. [Photo Memory Discovery Engine](https://photo-recall-research.vercel.app/engine) — asks the research question first, then shows source-family intake and a staged collection-to-answer process. Transfer: a question-led first screen and visible source distribution.
3. [Retrieval Agent](https://photos-retrieval-observatory.madeinmistak.chatgpt.site/#questions) — four plain navigation choices, suggested questions, a visible evidence count, and an explicit message when open-ended AI synthesis is not connected. Transfer: separate question retrieval from model claims.
4. [Google Photo Live User Insights](https://google-photo-live-user-insights.vercel.app/) — dashboard cards, source distribution and an Ask area. Caution: compact numbers and “AI” badges can imply validation that the screen itself does not prove.
5. [Google Photos Retrieval Research](https://google-photos-ten.vercel.app/) — a prominent raw-to-relevant-to-episode funnel with exclusions and a clear in-scope definition. Transfer: make each number’s stage and unit understandable.
6. [Google Photos Discovery Engine](https://google-photos-discovery-engine.vercel.app/) — short issue labels and click-through source quotes, but also a broad category that includes data loss outside the narrower retrieval question. Caution: do not let a large but adjacent category dominate the answer.
7. [Google Photos Search Insights](https://next-leap-google-photos-discovery-e.vercel.app/) — names in-scope, out-of-scope and success counts separately, then shows the cleaning and coding flow. Transfer: display exclusions and ordinary success without treating them as failures.

## Public repository workflows inspected

8. [Priyanka Gupta](https://github.com/priyanka-gupta169/Google-Photos-Discovery-Engine) — ingestion, relevance, extraction and opportunity matrix are separate steps; the README links live workbenches. Transfer: show the processing path in user language.
9. [Build with Niharika](https://github.com/buildwithniharika/google-photos-discovery-engine) — local commands separate collection, cleaning, labels, evaluation, extraction and clusters. Transfer: an AI output is a stage, not an insight by itself.
10. [Aashrita Malviya](https://github.com/aashritamalviya1999/google-photos-discovery-engine) — source-span and review status are explicit. Transfer: evidence anchors; do not repeat its unverified “zero hallucination” claim.
11. [Gokul Roshin](https://github.com/gokulroshin/google-photos-discovery-engine) — source-to-preprocessing-to-extraction pipeline is diagrammed. Transfer: a small flow diagram, not architecture jargon on the opening screen.
12. [Yukti](https://github.com/yukti1010/google-photos-discovery-engine) — short public description confirms the research purpose; README provides too little UI detail for a layout recommendation.
13. [Komal Mestri](https://github.com/komalmestri28-source/Google-Photos-discovery-Engine) — public README is very short; no UI recommendation drawn.
14. [Parvathy Suresh](https://github.com/rparvathysuresh/google-photos-discovery-engine) — staged collect/filter/extract/cluster workflow. Caution: its mock fallback and automated collection claims cannot become our evidence or permissions.
15. [Smit Shah](https://github.com/smitshah769-lang/google-photos-discovery-engine) — one-time snapshot and RAG are distinguished from a live research run. Transfer: disclose when the corpus was last processed and what the answer mode actually is.

Additional source check: [Aditi Verma](https://github.com/aditiverma898-blip/google-photos-discovery-engine) explicitly uses four primary views and distinguishes a large feedback intake from verified retrieval failures. [Pankaj Shrivastava](https://github.com/Pankaj-Shrivastava/GooglePhotos-DiscoveryEngine) labels its verbatims simulated; therefore its polished counts are a UI reference only.

## Decision for this engine

Use the evaluator sequence **purpose → data actually collected → where inputs were filtered → nine question answers → source and counterexample → provisional opportunity comparison → AI quality**. The left navigation names those tasks in everyday English and keeps all options visible. The opening screen shows **conversation items saved, app reviews analysed, source families with usable evidence, and approved answers**. Put internal control rows, coding terminology and quota telemetry in the research tools page.

Show source distribution by family, then a separate preliminary distribution of journey points and exit forms. Every chart names its denominator and review status. This is **not** a population chart, a Groww retention rate, or an automatic opportunity ranking. The question view explains **what the source says, why that interpretation is plausible, what could also explain it, and what remains unknown**.

**Reversal condition:** if new target-fit, source-checked Groww episodes or a validated model run materially change the evidence base, the displayed counts and answers must come from the ledger, not a hard-coded presentation snapshot.
